# Accounts and setup

One ordered path from an empty machine to a live product: which account you sign
into, what it costs, what it gives you, and **exactly which file in this repo**
each credential lands in.

Start at Stage 0 — it needs no accounts at all. Add each later stage only when
you actually need what it unlocks.

---

## 1. Every account, at a glance

| # | Account | Sign in at | Cost | Unlocks | Needed at |
|---|---|---|---|---|---|
| 1 | **Google account** | <https://accounts.google.com> | Free | Owns everything below | Stage 1 |
| 2 | **Firebase project** (Blaze plan) | <https://console.firebase.google.com> | Card required, **~$0 in practice** | Auth, Firestore, Storage, Functions, FCM, Hosting | Stage 1 |
| 3 | **Google Cloud console** | <https://console.cloud.google.com> | Free — same login, project auto-created | Budget alerts, quota caps, Secret Manager | Stage 1 |
| 4 | **Expo / EAS** | <https://expo.dev> | Free tier | Cloud builds of the APK / AAB / IPA, OTA updates | Stage 4 |
| 5 | **Google Play Console** | <https://play.google.com/console> | **$25 once** | Android release + Play Billing | Stage 5 |
| 6 | **Apple Developer Program** | <https://developer.apple.com> | **$99 / year** | iOS release + Apple IAP | Stage 5 (skip if Android-first) |
| 7 | Domain registrar *(optional)* | any | ~$10 / year | `forextradehub.app` on the landing page and admin | Stage 6 |

**Minimum to have a genuinely working product: accounts 1–3.** That is one
Google login. Everything else is about distribution, not about the backend
working.

Why Blaze and not the free Spark plan: Cloud Functions cannot be deployed on
Spark, and since 3 February 2026 Cloud Storage requires a billing account too.
Blaze keeps the same free quotas and bills only above them — at a few hundred
active users that bill is zero. Set the budget alert in Stage 1.2 and you will
never be surprised.

## 2. Credential map — what goes where

This is the table to keep open while you work. Every row's destination is
already covered by `.gitignore`; **none of these files should ever be committed.**

| Credential | Where you get it | Where it goes | In git? |
|---|---|---|---|
| Firebase **Android** config | Firebase console → Project settings → Android app → *google-services.json* | `mobile/google-services.json` | ❌ ignored |
| Firebase **iOS** config | same screen → iOS app → *GoogleService-Info.plist* | `mobile/GoogleService-Info.plist` | ❌ ignored |
| Firebase **web** config (6 values) | same screen → Web app → SDK setup | `admin/.env` as `VITE_FIREBASE_*` | ❌ ignored |
| **Admin service account** JSON | Project settings → Service accounts → Generate new private key | Anywhere **outside** the repo; pointed at by `GOOGLE_APPLICATION_CREDENTIALS` | ❌ never |
| **APNs auth key** (`.p8`) | Apple Developer → Certificates, IDs & Profiles → Keys | *Uploaded* to Firebase console → Cloud Messaging → Apple app config | ❌ never |
| **App Store Connect API key** (`.p8`) | App Store Connect → Users and Access → Integrations | `firebase functions:secrets:set APPLE_PRIVATE_KEY` — Secret Manager, not a file | ❌ never |
| Apple **Issuer ID**, **Key ID** | same screen | `backend/functions/.env.<project-id>` as function params | ❌ ignored |
| **Play billing access** | Play Console → Setup → API access | An IAM grant to `<project-id>@appspot.gserviceaccount.com` — no file | n/a |
| **EAS project id** | `eas init` (or expo.dev) | `mobile/.env` → `EAS_PROJECT_ID` | ❌ ignored |
| **Android upload keystore** | Generated by `eas credentials -p android` | Held by EAS; a local copy is `*.keystore` | ❌ never |
| **Play Store listing URL** | Play Console, once published | `admin/.env` → `VITE_PLAY_STORE_URL` | ❌ ignored |

> The Firebase web config and the two mobile config files are *public
> identifiers*, not secrets — what actually protects the product is the security
> rules plus the `admin` custom claim. They are still gitignored so a public
> repository does not advertise your project id. Supply them to CI through EAS
> secrets and GitHub Actions secrets.

## 3. Who logs into what, in the running product

There is **no separate admin account system**. Both surfaces authenticate against
the same Firebase Auth user pool with email and password:

| Surface | Who signs in | What gates access |
|---|---|---|
| Mobile app `(auth)/login` | Any member | A valid Firebase Auth account |
| Admin dashboard `/login` → `/admin` | The same kind of account | The **`admin` custom claim** on that user |

The claim is minted only by Cloud Functions (`setUserRole`), and the Firestore
rules read the claim — never a document field. So promoting someone is a server
action, and no user can promote themselves by editing their own profile.

- **First admin:** created by the seed script in Stage 3.
- **Every admin after that:** Admin dashboard → Users → set role. Roles are
  `user`, `moderator`, `admin`. See `docs/ADMIN_SETUP.md` §2.
- After any role or plan change the user must **sign out and back in** — the new
  claim rides in a freshly issued token. (`mergeClaims` revokes refresh tokens so
  a downgrade bites immediately.)

## Stage 0 — Run it today, with no accounts

Two independent ways to see the product working before you sign up for anything.

**A. Demo mode — the app with no backend at all.** Runs off an in-memory
dataset; no Firebase project, no network, no sign-in.

```bash
cd mobile && npm install
npm run build:demo        # checks the toolchain, then builds a standalone APK
```

Or run it on a connected device without packaging:

```bash
cp .env.example .env && echo "EXPO_PUBLIC_DEMO_MODE=1" >> .env
npm run prebuild && npm run android
```

Details in `docs/DEMO_BUILD.md`.

**B. Emulator suite — the *real* backend, locally, free.** Auth, Firestore,
Functions, Storage and Pub/Sub all run on your machine with your real rules and
your real function code.

```bash
npm i -g firebase-tools
cd backend/functions && npm install && cd ..
firebase emulators:start          # UI on http://localhost:4000
```

Then point the clients at it:

```bash
# mobile/.env
EXPO_PUBLIC_USE_FIREBASE_EMULATOR=1
EXPO_PUBLIC_EMULATOR_HOST=192.168.1.50   # your LAN IP if testing on a real device

# admin/.env
VITE_USE_EMULATOR=1
```

The emulator connection is guarded by `__DEV__` and cannot be switched on in a
release build. **Do all of your frontend and backend development here** — you
only need a paid plan the day you deploy.

## Stage 1 — Google + Firebase

### 1.1 Create the project

<https://console.firebase.google.com> → **Add project** → name it
`forextradehub-prod` → keep Google Analytics on (Crashlytics needs it).

Consider a second `forextradehub-dev` project and switch with `firebase use`.

### 1.2 Upgrade to Blaze, then immediately cap the risk

1. Console → ⚙ → **Usage and billing** → **Modify plan** → Blaze → attach a
   billing account.
2. Google Cloud console → **Billing → Budgets & alerts** → new budget, **$1**,
   alert at 50 / 90 / 100%.
3. Firebase console → **App Check** → register both apps (Play Integrity for
   Android, DeviceCheck/App Attest for iOS, reCAPTCHA for the web) and turn on
   enforcement for Firestore, Storage and Functions. This is the single biggest
   protection against an abuse-driven bill.

### 1.3 Enable the services

| Service | What to do |
|---|---|
| **Authentication** | Sign-in method → enable **Email/Password** |
| **Firestore** | Create database → **Production mode** → pick a region near your users — **it cannot be changed later** |
| **Storage** | Get started → Production mode → same region |
| **Cloud Messaging** | On by default |
| **Crashlytics** | Enable from the console |
| **Hosting** | Get started (used in Stage 6) |

> The Cloud Functions in this repo are pinned to `us-central1`
> (`backend/functions/src/index.ts`). Keep Firestore in the same region, or
> change that one line, or you pay cross-region egress on every trigger.

### 1.4 Register the three apps and place the config files

**Android** — Project settings → Add app → Android

- Package name: `com.forextradehub.app` (must match `APP_BUNDLE_ID` in `mobile/.env`)
- Download `google-services.json` → save as **`mobile/google-services.json`**
- For release builds add your SHA-1 and SHA-256 (get them with `eas credentials -p android`)

**iOS** — Project settings → Add app → iOS

- Bundle ID: `com.forextradehub.app`
- Download `GoogleService-Info.plist` → save as **`mobile/GoogleService-Info.plist`**
- Cloud Messaging → Apple app configuration → upload your **APNs auth key**.
  Without it, iOS push silently does nothing.

**Web** — Project settings → Add app → Web. Copy the six values into
**`admin/.env`**:

```bash
cd admin && cp .env.example .env
```

```ini
VITE_FIREBASE_API_KEY=AIza...
VITE_FIREBASE_AUTH_DOMAIN=forextradehub-prod.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=forextradehub-prod
VITE_FIREBASE_STORAGE_BUCKET=forextradehub-prod.firebasestorage.app
VITE_FIREBASE_MESSAGING_SENDER_ID=1234567890
VITE_FIREBASE_APP_ID=1:1234567890:web:abc123
VITE_USE_EMULATOR=0
VITE_PLAY_STORE_URL=https://play.google.com/store/apps/details?id=com.forextradehub.app
```

And **`mobile/.env`**:

```bash
cd ../mobile && cp .env.example .env
```

```ini
APP_NAME=Forex Trade Hub
APP_BUNDLE_ID=com.forextradehub.app
EAS_PROJECT_ID=                       # filled in at Stage 4
SUPPORT_EMAIL=support@forextradehub.app
TERMS_URL=https://forextradehub.app/terms
PRIVACY_URL=https://forextradehub.app/privacy
EXPO_PUBLIC_USE_FIREBASE_EMULATOR=0
```

## Stage 2 — Deploy the backend

```bash
cd backend
firebase login
firebase use --add                    # pick the project, alias it "default"
cd functions && npm install && cd ..

firebase deploy --only firestore:rules,firestore:indexes,storage
firebase deploy --only functions
```

That publishes ~25 Cloud Functions, the security rules for ~25 collections, the
composite indexes and the Storage rules.

Deploy indexes **before** first use — a missing composite index shows up at
runtime as `failed-precondition` with a console link, not as a build error.

Check it landed: `firebase functions:list` and `firebase functions:log`.

## Stage 3 — Seed the database and become the first admin

Register an account in the app first — the script promotes an account that
already exists.

```bash
# Firebase console → Project settings → Service accounts → Generate new private key
export GOOGLE_APPLICATION_CREDENTIALS=/absolute/path/outside/the/repo/service-account.json
export FIREBASE_PROJECT_ID=forextradehub-prod
export ADMIN_EMAIL=you@example.com

cd backend/functions
npx ts-node scripts/seed.ts
```

This writes `app_settings/config`, the community room, market quotes, three
signals, two articles, a course with three lessons, a poll and today's brief —
and sets your `admin` claim. It is idempotent, so re-running updates rather than
duplicates.

**Sign out and back in** so the claim reaches your token. Then
`cd admin && npm run dev` → <http://localhost:5173> → **Log in** → you land on
`/admin`.

## Stage 4 — Expo / EAS, for real builds

```bash
npm i -g eas-cli
eas login                    # free account at expo.dev
cd mobile
eas build:configure          # links the project and writes its id
```

Copy that project id into `mobile/.env` as `EAS_PROJECT_ID` — `app.config.ts`
reads it from there.

Give the cloud builder the Firebase config files, since they are gitignored:

```bash
eas secret:create --scope project --name GOOGLE_SERVICES_JSON --type file --value ./google-services.json
eas secret:create --scope project --name GOOGLE_SERVICES_PLIST --type file --value ./GoogleService-Info.plist
```

Then build — `docs/BUILD_AND_RELEASE.md` has the full matrix:

```bash
npm run build:apk     # APK for testing      (eas build -p android --profile preview)
npm run build:aab     # AAB for Google Play  (eas build -p android --profile production)
npm run build:ios     # IPA for the App Store
```

EAS generates and stores the Android upload keystore for you (`eas credentials`).
Losing it means you cannot update the listing, so export a backup and keep it
somewhere safe.

## Stage 5 — Stores and payments

Only needed when you are ready to charge. Everything else works without it.

### 5.1 Create the subscription products

Both stores need three auto-renewing products whose IDs match
`app_settings/config.products`:

```
forextradehub.premium.monthly
forextradehub.premium.quarterly
forextradehub.premium.yearly
```

### 5.2 Apple

1. App Store Connect → **Users and Access → Integrations → App Store Connect API**
2. Create a key with the **App Manager** role, download the `.p8` (offered once)
3. Note the **Issuer ID** and **Key ID**

```bash
cd backend
firebase functions:secrets:set APPLE_PRIVATE_KEY     # paste the whole .p8 contents
```

The non-secret values are v2 function **params**, read via `defineString`. Put
them in `backend/functions/.env.<project-id>` (gitignored), or let the CLI prompt
you at deploy time:

```ini
APPLE_ISSUER_ID=57246542-96fe-1a63-e053-0824d011072a
APPLE_KEY_ID=2X9R4HXF34
APPLE_BUNDLE_ID=com.forextradehub.app
ANDROID_PACKAGE_NAME=com.forextradehub.app
```

*(The older `firebase functions:config:set` mechanism is not what this code
reads — it uses `firebase-functions/params`.)*

**Server notifications:** App Store Connect → your app → App Information → **App
Store Server Notifications**, **Version 2**, production and sandbox URLs both:

```
https://us-central1-<project-id>.cloudfunctions.net/appStoreNotifications
```

### 5.3 Google Play

1. Play Console → **Setup → API access** → link your Google Cloud project
2. Grant `<project-id>@appspot.gserviceaccount.com` the **View financial data**
   and **Manage orders and subscriptions** permissions
3. Monetisation setup → set a Pub/Sub topic for real-time developer
   notifications, then add a **push** subscription on that topic pointing at:

```
https://us-central1-<project-id>.cloudfunctions.net/playNotifications
```

Redeploy the functions after setting secrets and params:

```bash
firebase deploy --only functions
```

## Stage 6 — Publish the landing page and the admin dashboard

`backend/firebase.json` already points Hosting at `../admin/dist`, and rewrites
everything to `index.html` so the client-side routes (`/`, `/login`, `/admin/*`)
resolve.

```bash
cd admin && npm run build
cd ../backend && firebase deploy --only hosting
```

Live on `https://<project-id>.web.app`. For your own domain: Firebase console →
Hosting → **Add custom domain** → `forextradehub.app`, then add the two A records
at your registrar. Certificates are issued automatically.

Once the Play listing is live, set the real URL and rebuild:

```ini
# admin/.env
VITE_PLAY_STORE_URL=https://play.google.com/store/apps/details?id=com.forextradehub.app
```

## Verify the whole chain

| Check | How |
|---|---|
| Auth works | Register in the app → a `users/{uid}` document appears |
| Claims minted | After seeding and re-login, your user carries `admin` |
| Rules enforced | As a free user, reading a premium signal fails `permission-denied` |
| Functions live | `firebase functions:log` shows `onUserCreated` on registration |
| Push works | Publish a signal from the admin panel → the device receives it |
| Teasers work | As a free user, today's premium signals render as locked cards |
| Admin gate | A non-admin signing in at `/login` is refused `/admin` |
| Payments | Sandbox purchase → `subscriptions/{uid}` written and `plan: premium` minted |
| Landing | `https://<project-id>.web.app` serves `/`, and Log in reaches `/login` |

## Order, time and cost

| Stage | Accounts | Time | Cost |
|---|---|---|---|
| 0 — local, emulator or demo | none | 15 min | $0 |
| 1 — Firebase project | Google | 30 min | $0 (card on file) |
| 2 — deploy backend | — | 10 min | $0 |
| 3 — seed + first admin | — | 10 min | $0 |
| 4 — EAS builds | Expo | 20 min | $0 |
| 5 — stores + payments | Play, Apple | 1–2 h + review | $25 once, $99/yr |
| 6 — hosting + domain | registrar | 20 min | ~$10/yr |

Running cost after launch is **$0 up to roughly 300 daily active users**, then
low single-digit dollars per month. The dominant driver is Firestore reads from
the live chat and signal listeners; every listener in this codebase is already
bounded with `limit()`.
